## 4. 전략 후보 비교

### 후보 A — 자체 구현 계속 확장 (M30 2·3단계 완주 + α)
Markdown 단일 소스 유지. `RichBlockEditor`에 블록 분할/병합·드래그·자체 undo 스택·표/수식 편집기를 자체 구현.
- 장점: 기존 결정 전부 무번복. 의존 0 유지. 기존 코드 연속.
- 단점: **자체 undo 스택 + 블록 간 구조 조작 + IME 안전**의 동시 성립은 ProseMirror가 수년 걸려 푼 문제군이다.
  기능마다 R29·R31이 곱으로 증식. 표·수식·다단·중첩 블록으로 갈수록 Markdown 왕복 계약이 병목.
  **Notion급 도달 비용이 세 후보 중 최대, 도달 확률은 최저.**

### 후보 B — 블록 편집 엔진 도입: **BlockNote** (권고 — 채택 판정은 M31 집중 분석 후 위임, §10 D2)
ProseMirror/Tiptap 위에 Notion형 UX(슬래시 메뉴·드래그 핸들·블록 중첩·표·이미지 블록·undo·기본 모바일
대응)를 기본 내장한 오픈소스. 2026-08 현재 활발히 릴리스 중(v0.54, 2026-08-13).
**정정(M31 실측 — 2026-08-15)**: 수식(KaTeX)·다이어그램(mermaid)은 코어 미내장이나 v0.54.0에서 **무료 MPL
별도 패키지**(@blocknote/math-block·diagram-block)로 출시 — 무료 범위에서 충족(성숙도는 M32~M33 검증).
찾기/바꾸기·목차(TOC)는 부재 — M35 자체 구현(상세 = `editor-v2.m31-analysis.md` §2).
**라이선스(2026-08-15 확인 — 초안의 "MIT" 표기는 오류, 정정)**: 코어 패키지(@blocknote/core·react 등)는
**MPL-2.0**(파일 단위 카피레프트 — 앱 코드 전염 없음, 의존성 사용에 제약 없음). **XL 패키지**(@blocknote/xl-*:
다단 레이아웃·PDF/DOCX 내보내기·AI)는 **GPL-3.0 듀얼**(GPL 비호환 시 상용 구독).
**전제(2026-08-15 사용자 고지): 본 앱 저장소는 GitHub public — 소스 공개 = 배포로 간주하는 보수적 해석을
채택한다.** 따라서 코어(MPL)는 공개 저장소 의존으로 문제없으나, **XL(GPL)은 앱 라이선스가 GPL-3.0 호환이
아닌 한 편입 불가.** → **D10 확정(2026-08-15 사용자): 라이선스가 걸리는 패키지는 도입하지 않는다 — 해당
기능(다단 등)은 후순위로 미뤄 자체 커스텀 블록으로 구현한다.** **1차 범위 = 코어(MPL)만.**
커스텀 블록/인라인 스펙을 TypeScript로 정의 가능 — F52 방언(형광펜·스포일러·글자색)·F43 참조 칩·콜아웃을
커스텀 스펙으로 이식한다.
- 장점: Notion급 UX의 대부분을 **검증된 엔진에서 상속**(undo = ProseMirror history, IME = ProseMirror의 성숙한 처리).
  구현량이 "엔진 제작"에서 "블록 스펙 정의 + 변환기"로 줄어든다. 모듈식(블록 스펙 = 모듈)이 프레임워크 차원에서 성립.
- 단점: **0.x 버전**(마이너 브레이킹 체인지 리스크 — 버전 고정 + 어댑터 계층으로 완충). 번들 증가(실측 필요, R32-c).
  테마 토큰 결선 작업. 저장 모델 전환(§5.2)이 수반.

### 후보 C — Tiptap 직접 조립
BlockNote가 서 있는 기반을 직접 조립. 자유도 최대, 구현량은 A와 B 사이(슬래시 메뉴·드래그 핸들·블록 UX를 직접 제작).
- 평가: B가 한계에 부딪히면 **같은 기반(Tiptap/ProseMirror) 위에서 하강 이주가 가능**하므로, C는 1차 선택이 아니라
  **B의 퇴로**로 두는 것이 합리적.

### 권고
**B(BlockNote) 채택, C를 구조적 퇴로로, 전환기 내내 기존 편집기(A의 산출물)를 기능 플래그 퇴로로 유지.**
근거: ① 목표가 Notion급으로 상향된 이상 "엔진을 만들 것인가, 쓸 것인가"의 문제이고, 개인 학습 앱에서 엔진 제작은
목적 전도다 ② 장기 캡처 파이프라인(§7.3)은 블록 단위 메타데이터(출처·시각·정제 이력)를 요구하는데 이는
블록 모델의 자연 속성이다 ③ R32가 경고한 "파서 2개"는 자체 변환기(D4)로 회피 가능해졌다.

## 5. 목표 아키텍처 — 완전 모듈식

### 5.1 계층 구조

```
[입력 소스]                [콘텐츠 코어]                    [소비 표면]
 키보드/붙여넣기 ─┐   ┌─ 블록 스키마 레지스트리 ─┐   ┌─ 에디터 뷰(BlockNote)
 이미지 업로드   ─┼─→ │  (블록 타입 = 모듈 단위)  │ ←─┼─ 리더 뷰(MarkdownView, 전환기)
 (v2.x) 녹음     ─┤   │  블록 JSON 문서 트리      │   ├─ 퀴즈/인쇄/플래시카드
 (v2.x) 사진/필기─┘   └─ 변환 계층(mdast↔블록)  ─┘   └─ LLM(반입·해설·정제)
        ↑ LLM 정제 파이프라인(IngestSource 인터페이스)
```

### 5.2 콘텐츠 코어 — 저장 모델 (D1)

- **소스 오브 트루스 = 블록 JSON**(`documents.content_blocks`): BlockNote 스키마 그대로가 아니라
  **앱 소유의 중립 블록 스키마**(버전 필드 포함)로 저장 — 엔진 교체(B→C) 시에도 저장분이 인질이 되지 않는다.
- **Markdown 프로젝션 유지**(`documents.content` 존치): 저장 시 블록→방언 Markdown을 **결정적으로 파생**해 함께 기록.
  파생 전용(역방향 편집 없음)이므로 이원화 드리프트가 원리상 없다. 용도: ① 전환기 리더 뷰(`MarkdownView` 무변경 —
  R32-b 충족) ② LLM 입출력(반입·해설 생성은 Markdown이 강함) ③ 검색(FTS)·인쇄 ④ 백업 가독성.
- Markdown으로 표현 불가한 블록(다단 등)은 프로젝션에서 **명시 규칙으로 강등**(예: 다단→순차 나열)하고
  프로젝션 손실 목록을 문서화한다. 1차 범위에서는 방언이 표현 가능한 블록 팔레트로 제한하는 안도 가능(D6).
- `explanation`도 동일 구조(`explanation_blocks` + 프로젝션). `choices`는 §7.2 참조.

### 5.3 변환 계층 (D4)

- **Markdown→블록**: 기존 remark 파이프라인(F52 방언 플러그인 포함)으로 mdast 생성 → **mdast→블록 변환기**(신규, 앱 소유).
  마이그레이션·LLM 산출물 반입·붙여넣기 공용. **Markdown 파서는 여전히 remark 1개** — F42/R19 원칙 유지.
- **블록→Markdown**: 프로젝션 직렬화기(신규, 앱 소유). DoD = 전 문서 코퍼스 왕복 검증
  (`s30-roundtrip.mjs` 코퍼스 재활용: Markdown→블록→Markdown 동형성) — R32-a 충족.
- **HTML 붙여넣기**: 기존 `htmlPasteMarkdown` 화이트리스트 계약(R30) 유지 — HTML→방언 Markdown→블록 경로로 통일.

### 5.4 블록 스키마 레지스트리 — 모듈 단위

블록 타입 하나 = 모듈 하나(스펙 파일 1개): `{ 데이터 스키마, 에디터 뷰, Markdown 프로젝션 규칙, (선택) 리더 뷰 }`.

| 묶음 | 블록 타입 | 비고 |
|---|---|---|
| 코어(엔진 내장) | 문단·헤딩·목록(중첩)·인용·코드·표·수식·이미지(**크기 조절** 포함)·**가로 구분선** | BlockNote 코어(MPL) 기본 + 설정 |
| 방언 이식(커스텀) | 콜아웃(F52)·인라인: 형광펜/밑줄/글자색/스포일러(F52)·참조 칩 3종(F43)·**문서 임베드(F43 트랜스클루전의 리치 표면 계승)** | 인라인 스펙 + 커스텀 블록 |

**참조 칩 UX 재설계 요구(2026-08-15 사용자 실기기 피드백 — M33 방언 이식 설계 시 확정, 구현 보류)**:
M31 PoC의 칩 버튼은 스펙 성립 증거일 뿐 UX가 아니다(대상 하드코딩 + 선택 텍스트를 대체하며 삽입 —
"글자가 사라지면서 참조 문서 7이 되는" 현상). 재설계 시 확정할 것:
① **대상 선택** — 삽입 시 어떤 문서/문제/개념을 참조할지 고르는 피커 필수(검색·최근 문서. 기존 F43 참조
문법의 대상 해석 규칙 계승). 하드코딩·무피커 즉시 삽입 금지.
② **선택 텍스트 보존** — 텍스트를 드래그한 상태의 삽입이 선택 영역을 파괴하지 않아야 한다. 원칙:
칩 삽입은 **커서 위치 삽입**으로 한정하고, 선택 상태에서는 (a) 선택 텍스트를 칩 라벨로 승계하거나
(b) 선택 해제 후 커서 삽입 중 택일 — M33 설계에서 결정.
③ **라벨 규칙** — 기본 라벨 = 대상 문서 제목(대상 변경·제목 변경 시 추종 여부 포함), 사용자 지정 라벨
허용 여부, 칩 클릭 시 동작(이동 vs 미리보기 — 기존 F43 동작과의 일관성)을 함께 확정.
④ **문법 왕복** — 칩의 Markdown 프로젝션은 기존 F43 참조 문법으로 강등(§5.2) — 위 결정과 모순되지
않는지 M32 변환기 설계에서 교차 검증.

### 5.5 입력 파이프라인 인터페이스 (v2.00.0은 설계만, 구현은 v2.x)

`IngestSource(녹음|사진|메모|필기) → 원본 보관(sources/, 불변 규칙 4) → LLM 정제 잡(비동기 큐, 기존 잡 패턴 재사용)

휴대폰은 기존 홈 네트워크 접속(R12 유지) + PWA로 커버 — 별도 앱 없음.

## 6. 데이터 모델 영향 (초안 — 확정 시 plan §6.2 + Alembic)

```sql
-- documents 확장 (후보안 B 확정 시)
ALTER TABLE documents ADD COLUMN content_blocks TEXT;      -- 블록 JSON (버전 필드 포함), NULL = 미전환 문서
ALTER TABLE documents ADD COLUMN explanation_blocks TEXT;  -- 동일
-- content·explanation 컬럼은 존치 — 프로젝션 저장소로 역할 전환 (렌더·LLM·검색·백업 호환)

-- 노트(베타) — M33에서 신설 (D9 드래프트 격리: documents 무접촉의 착지 표면. 확정 시 §6.2 정식 등재)
CREATE TABLE notes (
  id             INTEGER PRIMARY KEY,
  title          TEXT,
  content_blocks TEXT NOT NULL,   -- 앱 중립 블록 JSON (blocks_version 포함)
  content        TEXT,            -- Markdown 프로젝션 (파생 전용)
  is_active      INTEGER DEFAULT 1,
  created_at     DATETIME, updated_at DATETIME
);
```
- 마이그레이션: 일괄 변환하지 않고 **열람·편집 시 지연 전환**(lazy) + 배치 변환 스크립트 별도 제공 —
  변환기 검증(§5.3 DoD) 통과 후에만. 미전환 문서는 기존 편집기로 그대로 열린다(퇴로 겸용).
- `blocks_version` 필드로 스키마 진화 대비. 백업(F27)은 무변경(같은 DB 파일).

## 12. 개발 방식 — 드래프트 격리 (D9, 확정 2026-08-15)

사용자 제안("완전히 드래프트해서 원본을 건드리지 말고 노트 기능을 완성하고 main에 탑재")의 이행 규칙.

1. **코드 격리**: 새 편집기 코드는 격리 디렉터리(가칭 `frontend/src/editor2/`)에만 둔다.
   기존 편집기 파일(`MarkdownFieldEditor`·`EditablePreview`·`RichBlockEditor`·`DocEditor`)과
   기존 렌더러(`MarkdownView`)는 **무수정** — v1.90.1 편집 경험은 탑재(M34) 전까지 1바이트도 변하지 않는다.
2. **표면 격리**: 진입점은 신규 **"노트(베타)"** 표면(라우트/패널)뿐. 저장도 신규 `notes` 테이블(§6)로
   documents와 완전 분리 — 실데이터 무위험 상태에서 실사용 검증(IME·모바일·왕복·UX)을 쌓는다.
3. **탑재 게이트(M34)**: 노트 베타에서 패리티 체크리스트 + 실사용 확인이 통과해야 documents에 연결한다.
   그 시점이 D1(저장 전환)의 최종 확정 시점이며, 실패 시 노트 베타만 남기고 documents는 현행 유지(무손실 철수).
4. **git 전술(위임 범위)**: 수개월짜리 장기 드래프트 브랜치는 쓰지 않는다 — main과의 드리프트·거대 일괄 머지·
   워크트리 소실 전례의 리스크가 크다. 대신 **stage 단위 소 PR을 계속 main에 머지**하되, 새 코드는 베타 표면
   뒤에서 비활성이므로 "원본 무접촉"이라는 격리 목적은 앱 수준에서 그대로 성립한다. main은 항상 안정.
5. **노트 기능의 겸용 가치**: 노트는 검증용 임시물이 아니라 존치 기능 — 강의 노트는 v2.x 캡처 파이프라인
   (녹음·사진·필기 → LLM 정제 → 삽입, §5.5)의 자연스러운 착지 표면이고, 추후 "노트 → 문제/개념 승격" 플로우의
   출발점이 된다.
