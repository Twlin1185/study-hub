> 배경: 필기 기출의 자동 수집 경로가 없음이 확정(M13·M14)된 뒤 **수동 반입이 정본 경로**가 됐다(F40). 사용자가 가진 자료는 PDF만이 아니다 — docx·xml·md·txt·html·xlsx 파일이 반입 경로에서 **정식으로**(조용한 실패 없이) 처리돼야 한다.

## 현행 실측 (2026-07-28 — 계획서 §14 F42 "실측 현황"이 정본, 여기는 요지)

- 파일 반입(`POST /api/convert`)에 **확장자 화이트리스트가 없다** — 어떤 파일이든 잡에 들어간다.
- 실효 지원은 엔진별: CLI = Claude Code Read 도구(텍스트·PDF·이미지) / API = PDF(base64 document 블록)·이미지 블록·**그 외 전부 utf-8 강제 디코드(`errors="replace"`) 본문 삽입**.
- 따라서 **docx/xlsx(zip 바이너리)는 mojibake로 조용히 LLM에 투입**된다 — 구조화 오류 없이 비용 지출 + 쓰레기/창작 산출 위험. **이 결함의 수정이 이 단계의 중심이다.**
- URL 반입 content-type 화이트리스트: pdf·html/xhtml·markdown·text/plain·이미지 4종 — xml·office 계열 MIME은 거부.
- 서버 파싱 라이브러리 0개(requirements 실측).

## 착수 시 선행 절차 (게이트 아님 — 결정·문서를 먼저 굳힌다)

- [ ] **D1. 파서 라이브러리 최종 채택** (계획서 F42 방침: 순수 파이썬·오프라인·포맷당 1개·계획서 등재 후 추가) — docx 후보: python-docx(lxml C 확장 의존 — wheel 설치 무해 여부 판단) vs docx2txt / xlsx 후보: openpyxl. 채택 결과를 계획서 F42에 등재.
- [ ] **D2. 세부 결정 5건** (계획서 F42 "착수 전 결정 필요" ②~⑥): 인코딩 판별 순서(잠정 utf-8 BOM→utf-8→cp949, chardet류 잠정 반대) · xlsx 직렬화 형식(시트별 Markdown 표 vs TSV)과 시트·행 상한 · csv 포함 여부 · URL content-type 확장 목록 · 추출 텍스트 길이 상한과 초과 안내 문구(F40-④ `invalid_output` 연계 — 서버측 자동 분할 금지).
- [ ] **D3(문서). 설계 §4.18 신설** — 지원 포맷 매트릭스(포맷×경로(파일/URL)×엔진(cli/api)), 판별 규칙(확장자+매직 바이트+텍스트성 검사), `unsupported_format` 안내 문구(포맷별 폴백 — 서버가 완성 문장 생성, §4.10 notes 관례), 추출 실패 시 `parse_failed` 재사용 여부. plan §6.2 DDL 변경 없음 전제를 설계에서 재확인(어긋나면 보고).

## 목표

끝났을 때, docx·xlsx·xml·md·txt·html 파일이 파일/URL 반입에서 **미리보기까지 완주**하거나, 지원 불가 파일이 **구조화 오류 + 폴백 안내**로 끝난다. 어떤 경로로도 "바이너리 mojibake가 조용히 LLM에 투입돼 비용만 쓰는" 일이 없다.

## 작업 체크리스트

> 권장 순서: **1(판별·거부 — 결함 수정) → 2(A군 정식화) → 3(B군 추출) → 4(URL·프론트) → 5(테스트) → 6(문서·매뉴얼)**.
> 1이 끝난 시점에 기존 지원 포맷(PDF·이미지·md/txt)이 회귀 없이 동작해야 한다(판별 계층 단독 배포 가능 상태).

### 1. 포맷 판별·거부 계층 (mojibake 조용 투입 차단)

- [ ] `convert_service`에 반입 파일 판별 단계 신설: 확장자 + 매직 바이트(zip 시그니처 `PK`·HWP 시그니처 등) + 텍스트성 검사(널 바이트·디코드 성공률) — 판별 결과를 잡에 기록(`phase='preparing'` 구간)
- [ ] 판별 불가 바이너리·미지원 포맷(hwp·zip·doc·xls 등) → `error_info.kind:'unsupported_format'` + **포맷별 폴백 안내**(서버가 완성 문장 — "한글에서 PDF로 변환 후 반입", "압축을 풀어 PDF/이미지를 파일 반입" 등 F35-3 관례). 원본은 sources/에 저장된 뒤 종료(조용한 스킵 금지 — qnet과 동일 정책)
- [ ] API 엔진의 무조건 utf-8 디코드 폴백(`_api_content_blocks_for_file`)을 판별 계층 통과분에만 적용 — **판별을 거치지 않은 바이너리가 텍스트로 흘러가는 경로 0**
- [ ] 회귀 확인: PDF·이미지·기존 텍스트 파일 반입이 판별 계층 추가 후에도 동일 동작 (스모크)

### 2. A군 — 텍스트 계열 정식화 (md·txt·html·xml)

- [ ] 인코딩 판별(D2 확정안: utf-8 BOM→utf-8→cp949 순 잠정) 후 텍스트 투입 — cp949 파일이 mojibake 없이 변환되는지 확인
- [ ] html은 원문 그대로 투입(서버측 태그 제거 파서 추가하지 않음 — LLM이 처리, 기존 URL 반입 경로와 동일). xml도 원문 투입
- [ ] CLI 엔진 경로: 텍스트 파일은 기존대로 파일 경로 전달(Claude Code Read — 변경 최소화), API 엔진 경로는 판별된 인코딩으로 디코드해 본문 삽입
- [ ] 추출·디코드된 텍스트 길이가 상한(D2) 초과 시 실행 전 안내(분할 권고 — LLM 비용 지출 전에 멈춘다)

### 3. B군 — 서버측 텍스트 추출 (docx·xlsx)

- [ ] D1 채택 파서를 requirements에 추가(버전 고정) — **포맷당 1개 원칙**
- [ ] docx: 문단·표 텍스트 추출 → A군과 같은 텍스트 투입 형태로 정규화. 수식(OMML)·이미지 소실은 한계로 수용(추출 결과에 소실 가능성 표시 여부는 설계 §4.18에서 확정)
- [ ] xlsx: 시트별 직렬화(D2 확정 형식) — 시트·행 상한 초과 시 안내(잘림 위치 명시)
- [ ] 파서 예외(암호 파일·손상 파일·구버전 포맷 위장) → `error_info` 구조화(`parse_failed` 또는 `unsupported_format` — 설계 확정안) + 폴백 안내. **파서 예외가 잡 크래시·조용한 실패가 되는 경로 0**
- [ ] 추출 텍스트는 저장하지 않는다(임시 파일만 — sources/에는 원본 바이트, R18 정신). LLM 사용량 사전 안내는 추출 텍스트 길이 기준으로 정확화

### 4. URL 반입·프론트

- [ ] URL content-type 화이트리스트 확장(D2 확정 목록 — xml·officedocument MIME 등) + 다운로드 후에도 1절 판별 계층 통과(content-type 사칭 방어 — 매직 바이트 우선)
- [ ] 반입 화면: 파일 선택 input에 지원 확장자 `accept` 힌트 + 안내 문구 갱신("PDF·이미지 등" → 지원 포맷 명시). 대기열(F40-②)·분류 경로 지정(F40-③)과의 조합 동작 확인
- [ ] `unsupported_format`·`parse_failed` 렌더가 포맷별 폴백 문구를 그대로 나열하는지 확인(프론트 포맷 분기 금지 — 서버 완성 문장 관례)
- [ ] 색상 하드코딩 금지(토큰만)

## DoD (완료 정의)

1. docx·xlsx·xml·md·txt·html 파일이 파일 반입에서 **미리보기까지 완주**한다(각 포맷 실파일 1건 이상 라이브 확인).
2. **바이너리 mojibake가 LLM에 투입되는 경로 0** — hwp·zip·손상 파일은 원본 저장 + `unsupported_format`/`parse_failed` 구조화 오류 + 폴백 안내로 끝난다.
3. cp949 텍스트 파일이 깨지지 않고 변환된다.
4. 기존 지원 경로(PDF·이미지·URL 반입·대기열 F40) 회귀 0.
5. 신규 의존은 D1 채택 파서만(계획서 F42 등재와 일치) — 그 외 라이브러리 추가 0건.
6. DDL 변경 0건·Alembic 0건 (설계 §4.18에서 재확인 — 어긋나면 착수 중단 후 보고).

## 이 단계에서 하지 않는 것

- **HWP 파서 도입** — 순수 파이썬 성숙 파서 부재. 폴백 안내(PDF 변환 후 반입) 유지 — F35-3 결정 그대로.
- **구버전 doc·xls 지원** — 지원 목록에서 명시 제외(docx·xlsx로 변환 안내). 실수요가 확인되면 계획서에 먼저 확정.
- **서버측 PDF 파싱·분할** — F40-④ 결정 유지(PDF는 LLM 직투입). pypdf 도입은 M15(원문 대조)의 몫.
- **OCR·이미지 내 텍스트 추출** — 이미지 반입은 기존 경로(LLM 비전) 그대로.
- **추출 텍스트의 저장·색인** — 재추출 가능한 파생물은 저장하지 않는다(R18 정신).
- **변환 프롬프트의 포맷별 분기 튜닝** — convert.md 단일본 유지(stage-15 원칙과 동일).
