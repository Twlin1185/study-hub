# 원본 자료 → Study Hub 반입 JSON 변환 프롬프트

> 이 문서는 Claude Code(또는 다른 LLM)에게 **기출/학습 원본 파일(PDF·MD·이미지·엑셀)** 을
> Study Hub 반입 규격 JSON으로 변환시키기 위한 지시서다.
> 사용법: 변환할 원본 파일과 함께 이 프롬프트를 전달 → 아래 규격에 맞는 `import/*.json` 생성 →
> 앱 `/import` 화면에서 미리보기·검증 후 반입.
>
> 규격 단일 출처: `docs/01-plan/study-app.plan.md` §8.2 / §8.3. 여기와 어긋나면 계획서가 우선.

---

## 0. 역할

너는 시험 기출문제·학습자료를 **구조화된 학습 문서(Document)** 로 정리하는 변환기다.
원본의 내용을 **그대로 보존**하되(오탈자 교정 수준의 최소 정리만), 앱이 학습·풀이·복습에
쓸 수 있는 JSON으로 재구성한다. **없는 정보를 지어내지 말 것** — 특히 정답/해설은 원본에
있을 때만 채우고, 불확실하면 비워 두고 `source_detail`로 원본 위치를 남긴다.

## 1. 출력 형식 (엄수)

- 출력은 **단 하나의 JSON 객체**. 코드펜스(```)·설명 문장·주석을 붙이지 말 것.
- 문자열은 UTF-8, 한글 그대로. 수식·코드는 Markdown으로.
- 최상위 형태:

```json
{
  "format_version": 1,
  "source": { "filename": "2023_2회_기출.pdf", "note": "정보처리기사 필기 2023년 2회" },
  "documents": [ /* 아래 문서 객체들 */ ]
}
```

- `format_version`: **항상 정수 1**.
- `source.filename`: 원본 파일명(있으면). `source.note`: 사람이 읽을 출처 설명(선택).
- `documents`: 문서 객체 배열. **순서가 곧 학습 순서**(§6 인터리브 배치 참조).

## 2. 문서 객체 필드

| 필드 | 필수 | 설명 |
|---|---|---|
| `type` | ✅ | `concept` \| `question` \| `past_question` \| `flashcard` (§3 판별 기준) |
| `title` | ✅ | 짧고 식별 가능한 제목. 기출은 `"2023-2회 17번: 정규화"`처럼 회차+번호+주제 |
| `content` | ✅ (개념·문제) | 본문/문제 지문 (Markdown). 이미지 `![](sources/images/xxx.png)` |
| `choices` | 객관식이면 | 보기 **문자열 배열**. 순서 = 보기 번호 순 |
| `answer` | **문제면 필수** | 정답. **객관식은 1-base 보기 번호 문자열만**(`"1"`~`"n"` — 보기 텍스트 금지). 단답은 정답 문자열 |
| `answer_source` | **문제면 필수** | `"original"`(정답이 원본에 명시돼 있음) \| `"solved"`(원본에 없어 **네가 풀어 채움**) |
| `explanation` | 권장 | 해설 (Markdown). 없으면 생략 |
| `difficulty` | 선택 | 1~5 정수. 애매하면 생략(넣지 말 것) |
| `tags` | 권장 | 문자열 배열 (§4) |
| `source_detail` | 권장 | `"2023년 2회 17번"` 등 원본 대조용 위치 |
| `suggest_categories` | 권장 | 분류 경로 문자열 배열 (§5) |
| `suggest_relations` | 선택 | 관련 기존 문서 번호(`"DOC-0012"`) 배열 (§5) |

- **필수 필드 누락 시** 앱 미리보기에서 해당 항목이 `error`로 잡혀 반입에서 제외된다.
  특히 `type in {question, past_question}` 인데 `answer`가 비면 오류다 — 정답을 못 찾으면
  차라리 `type: "concept"`(해설/정리)로 분류하거나, 사람이 채우도록 `answer`를 명확히 비워 표시.
- `difficulty`는 1~5 밖이면 오류. 확신 없으면 **넣지 말 것**.
- **`content`는 개념·문제(`concept`·`question`·`past_question`)에서 필수**다. 비면 오류.

### 2-1. `answer_source` — 정답의 출처를 스스로 신고하라 (엄수)

문제 타입(`question`·`past_question`)은 **반드시** `answer_source`를 넣는다.

- `"original"` — **정답이 원본에 명시돼 있고**, 그것을 그대로 옮겼다(정답표·해설·표시된 답 등).
- `"solved"` — 원본에 정답이 없어서 **네가 직접 풀어 채웠다**.

원본에 없는 정답을 `"original"`로 신고하지 마라. 확신이 없으면 `"solved"`다.
`"solved"` 항목은 앱 미리보기에서 경고 배지가 붙고 **기본적으로 반입에서 제외**되어,
사람이 하나씩 확인해 승인해야 들어간다 — 즉 `"solved"`는 잘못이 아니라 **정직한 신고**다.
정답을 지어내는 것보다 `"solved"`로 표시하거나 `type: "concept"`으로 돌리는 편이 항상 낫다.

### 2-2. 객관식 `answer`는 보기 번호만 (엄수)

- `choices`가 있으면 `answer`는 **`"1"`~`"n"` 범위의 1-base 보기 번호 문자열**이어야 한다.
- 보기 텍스트를 그대로 쓰지 마라(보기 자체가 숫자인 문제에서 번호/값이 뒤섞인다).
  예: `choices: ["12", "24", "36", "48"]`, 정답이 `36`이면 → `"answer": "3"`.
- 범위를 벗어나거나 번호가 아니면 해당 항목은 오류로 잡혀 반입에서 제외된다.

### 2-3. 지문·보기는 원본 문자열을 보존하라 (원문 대조가 있다)

앱은 반입 미리보기에서 **각 문항의 지문·보기가 원본 텍스트에 실재하는지 서버가 기계적으로
대조**한다. 원본에 없는 문자열은 `창작 의심` 경고가 붙고 기본 반입에서 제외된다.

- 추출이 깨져 읽을 수 없는 부분(수식·기호·표)을 **그럴듯하게 메우지 마라.**
  읽을 수 없으면 그 문항은 만들지 말거나, `content`에 `(원본 확인 필요)`라고 남긴다.
- 보기 4개 중 일부만 읽힌다고 나머지를 **지어내지 마라** — 문항 전체를 빼는 편이 낫다.
- 다듬기는 오탈자·줄바꿈 정리 수준까지만. 문장을 다시 쓰지 마라.

## 3. 타입 판별 기준

- **`past_question`** — 실제 시행된 시험의 기출문제. 회차·연도 정보가 있으면 우선 이 타입.
  `source_detail`에 회차/번호를 반드시 남긴다.
- **`question`** — 출처가 기출은 아니지만 정답이 있는 연습문제·예상문제.
- **`concept`** — 개념 설명·정리·요약. 정답이 없다. 학습 모드에서 "읽고 다음"으로 진행.
- **`flashcard`** — 앞면(질문)/뒷면(정답)의 짧은 암기 카드. `content`=앞면, `answer`=뒷면.
  긴 개념 설명은 flashcard가 아니라 `concept`으로.

> 판단 우선순위: 정답+보기 있고 시험 출처 → `past_question` / 정답 있고 시험 출처 아님 →
> `question` / 정답 없음 → `concept` / 짧은 암기쌍 → `flashcard`.

## 4. 태그 부여 지침

- 태그는 **주제·개념 키워드**. 예: `데이터베이스`, `정규화`, `트랜잭션`, `SQL`.
- `#` 기호 없이 순수 단어로. 표기 통일(예: `DB`와 `데이터베이스`가 섞이지 않게 한 형태로).
- 문서당 2~5개 권장. 과도한 태그 금지. 시험/회차는 태그가 아니라 `source_detail`/분류로.
- 같은 주제의 문제와 개념이 **같은 태그**를 공유하도록 → 나중에 태그 규칙·검색이 이어준다.

## 5. suggest_categories / suggest_relations 작성 규칙

### suggest_categories (분류 경로 제안)
- **경로 구성 규칙의 단일 출처는 `prompts/taxonomy.md`** — 반드시 그 정책을 따를 것. 요약:
  - **기출 문제 = 이중 연결**: `["<자격증>/<시험>/기출문제/<YYYY년 N회>", "<자격증>/<시험>/<과목명>"]`
    (회차 축 = 실전 풀이·인쇄, 과목 축 = 커리큘럼·약점 분석. 둘 다 제안한다.)
  - 연습문제·개념: `["<자격증>/<시험>/<과목명>"]` (개념은 단원을 알면 `/<단원>`까지)
  - 회차 표기는 `YYYY년 N회`로 통일 (예: `2020년 4회`).
- 형식: `"자격증/시험구분/과목/단원"` 처럼 **`/`로 구분한 계층 경로** 문자열.
- 앱은 이 경로를 루트부터 이름으로 탐색한다. **전부 존재하면 연결 제안**,
  일부/전부 없으면 **"생성 제안"** 으로 표시되고 사용자가 승인하면 노드를 만든다.
- 실제 트리 이름과 최대한 맞춰라(원본에 과목명이 있으면 그 이름 사용). 확신 없으면
  얕은 경로(`"정보처리기사/필기"`)라도 제안하는 편이 미분류보다 낫다.
- 한 문서를 여러 분류에 넣어야 하면 배열에 여러 경로를 담는다(다대다 연결).

### suggest_relations (문서 간 관계 제안)
- **이 문제를 설명하는 기존 개념 문서**의 번호(`"DOC-0012"`)를 배열로.
- 앱은 번호로 기존 문서를 찾아, 승인 시 `개념 → 문제`(`relation: explains`) 관계를 만든다.
- **존재하지 않는 번호는 경고 후 무시**되므로, 원본 안에서 새로 만드는 문서끼리는
  번호로 엮을 수 없다(아직 채번 전). 이미 DB에 있는 개념문서 번호를 알 때만 사용.
- 모르면 비워 둘 것(빈 배열). 억지 연결 금지.

## 6. 인터리브 배치(학습 순서) 지침

`documents` 배열의 **순서가 곧 학습 모드의 진행 순서**다(계획서 §9.2). 한 단원을 변환할 때:

- **개념 몇 개 → 확인문제 2~3개 → 다음 개념 …** 형태로 섞어 배치한다.
  (개념만 몰아넣거나 문제만 몰아넣지 말 것 — 읽고 바로 확인하는 흐름이 목표.)
- 권장 리듬 예: `concept, concept, question, question, concept, past_question, ...`
- 같은 주제 묶음은 인접시키고, 쉬운 것 → 어려운 것 순으로.
- flashcard는 해당 개념 뒤에 모아 두거나 별도 묶음으로.

## 7. 변환 체크리스트 (출력 전 self-check)

1. 최상위에 `format_version: 1`, `source`, `documents` 있는가.
2. 모든 문서에 `type`·`title` 있는가. 개념·문제에 `content` 있는가. 문제 타입에 `answer` 있는가.
3. 객관식 `answer`가 **보기 번호 문자열(`"1"`~`"n"`)** 인가 (보기 텍스트가 아닌가).
4. 문제 타입마다 `answer_source`(`"original"`|`"solved"`)를 **정직하게** 넣었는가.
5. `difficulty`는 넣었다면 1~5 정수인가.
6. `tags`·`suggest_categories`·`suggest_relations`는 **문자열 배열**인가.
7. 원본에 없는 지문·보기·정답·해설을 지어내지 않았는가 (서버가 원문 대조로 검사한다).
8. `documents` 순서가 개념↔문제 인터리브로 학습하기 좋은가.
9. 출력이 **코드펜스·설명 없는 순수 JSON 하나**인가 (코드펜스가 섞이면 변환 전체가 실패한다).

## 8. 최소 예시

```json
{
  "format_version": 1,
  "source": { "filename": "2023_2회_기출.pdf", "note": "정보처리기사 필기 2023년 2회" },
  "documents": [
    {
      "type": "concept",
      "title": "정규화(Normalization) 개요",
      "content": "정규화는 이상현상을 제거하기 위해 릴레이션을 분해하는 과정이다. 1NF→2NF→3NF→BCNF 순으로 진행된다...",
      "tags": ["데이터베이스", "정규화"],
      "source_detail": "이론 정리",
      "suggest_categories": ["정보처리기사/필기/데이터베이스"]
    },
    {
      "type": "past_question",
      "title": "2023-2회 17번: 제3정규형",
      "content": "다음 중 제3정규형(3NF)의 조건으로 옳은 것은?",
      "choices": ["이행적 함수 종속 제거", "부분 함수 종속 제거", "원자값만 허용", "결정자가 후보키"],
      "answer": "1",
      "answer_source": "original",
      "explanation": "3NF는 2NF를 만족하면서 이행적 함수 종속을 제거한 상태다.",
      "difficulty": 3,
      "tags": ["데이터베이스", "정규화"],
      "source_detail": "2023년 2회 17번",
      "suggest_categories": ["정보처리기사/필기/기출문제/2023년 2회", "정보처리기사/필기/데이터베이스"],
      "suggest_relations": []
    }
  ]
}
```
